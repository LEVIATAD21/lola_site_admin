# Mercado Pago: activation and acceptance

This branch implements Payment Brick (card/Pix) backed by Payments API, D1 order reservations and signed payment webhooks. Checkout remains disabled unless all dependencies are explicitly configured. No credentials or real payment data are included in this repository.

## Required server variables on lola-admin-api

- LOLA_PAYMENT_PROVIDER=mercadopago (selects the new finance view)
- LOLA_MP_ENABLED=false until sandbox acceptance is complete
- LOLA_MP_MODE=test initially; production only with the matching production account and credentials
- LOLA_MP_PUBLIC_KEY: public application credential
- LOLA_MP_ACCESS_TOKEN: encrypted secret; never frontend/build code
- LOLA_MP_WEBHOOK_SECRET: encrypted secret generated by the Mercado Pago application
- LOLA_MP_ACCOUNT_ID: numeric account user ID; validated against /users/me before charging
- LOLA_MP_PICKUP_DESCRIPTION: actual pickup address/instructions approved by the merchant

This initial implementation supports explicit pickup without freight. It does NOT calculate delivery rates. Do not enable it for shipped orders until shipping, merchant identity, contact information, privacy/returns terms and fulfillment conditions are complete. The merchant must approve the real pickup instructions before enabling payment.

Apply infra/d1/0005_mercado_pago_checkout.sql to the main catalog DB after testing on an isolated database. It creates order/limit tables and reservation/state triggers without creating products, customers or transactions. PHOTOS_DB remains exclusively for image bytes. Do not delete financial records to roll back: set LOLA_MP_ENABLED=false.

## Provider application

Choose Checkout Bricks / Payment Brick for card and Pix. Register the payment topic webhook:

https://lola-admin-api.pages.dev/api/webhooks/mercadopago

Use the application's matching webhook secret. The handler validates HMAC, a bounded timestamp and the resource ID; it then retrieves the payment using the server Access Token and checks account, currency, amount, environment and external order reference. Neither a browser success screen nor an unsigned notification marks an order as paid.

## Mandatory acceptance before production

- Run node --experimental-strip-types --test tests/mercadoPago.test.ts.
- Run both repository CI suites and CodeQL.
- Sandbox approved/refused cards and Pix pending-to-paid, expiry/cancellation, duplicate submissions and delayed/replayed webhooks.
- Verify the deployed CSP permits only the required SDK/API/iframe resources and the SDK renders correctly on mobile.
- Verify user reload/resume, lost network response and checkout closed with payment pending.
- Compare provider payment IDs/amounts with the admin Pedidos da loja view.
- Verify real merchant identity, pickup, policies and receipts before switching to production.
- Enter production secrets manually, redeploy, and enable only after the merchant authorizes real charges.

## Operational behavior and limits

Prices are calculated server-side from published catalog rows. Draft reservations expire after 15 minutes and are released on the next checkout creation. An ambiguous provider response retains the reservation; no second POST charge is attempted. The browser and authenticated admin reconciliation fetch the provider's status. Use Pedidos da loja > Conferir pagamentos for pending orders; monitor provider webhook delivery. A scheduled reconciler is not included in this change.

Approved payment debits physical stock exactly once. Rejection/cancellation releases the hold. Refund/chargeback does not automatically return stock, since a physical return must be checked. The finance refund list represents full refunded status; partial refunds and official receipts must be checked in the Mercado Pago account. This branch does not initiate refunds.

For payment uncertainty, reconcile before releasing reservations or attempting another charge. Retain the order ID. Tokens for reading an individual order are hashed in D1 and retained only in the buyer's browser session. No raw card numbers, CVV, payer identification or email are written to the order database or logs.
